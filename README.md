# d3d12-engine

Windows 11 / Direct3D 12 上で，レンダリングパイプライン・GPU リソース管理・シーン管理を自作しているレンダリングエンジンです．
物理量（測光量）に基づくライティングと露出，IBL（Image Based Lighting），HDR ディスプレイ出力，directional light のシャドウマッピングまでを実装しています．
今後はゲームエンジンとして使えるように機能を広げ，このエンジンを使うゲームを別リポジトリで制作する予定です．

|                  |                                                    |
| ---------------- | -------------------------------------------------- |
| 言語 / API       | C++20, Direct3D 12, HLSL（Shader Model 6.0 / DXC） |
| プラットフォーム | Windows 11 (Win32)                                 |
| 開発期間         | 2025年9月 〜 継続中                                |
| 開発体制         | 個人開発                                           |
| ビルド           | Visual Studio 2022 / vcpkg                         |

ゲームエンジン（Unity / Unreal Engine）やレンダリングフレームワークは使わず，Direct3D 12 API 上に描画・同期・メモリ管理を自前で実装しています．

## 実装している機能

| -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

| **リソース管理**     | インデックスと世代番号を組にしたハンドルによるオブジェクト管理，RAII によるディスクリプタとアップロードヒープの管理，GPU が使用中のリソースの遅延解放                                   |
| **アセット**         | Assimp による GLB/glTF の読み込み，DirectXTex によるテクスチャ処理，IES プロファイルのパースと光度テクスチャ化                                                                          |
| **デバッグ**         | base color・法線・roughness などの中間結果をそのまま表示するデバッグビュー（10種類），White Furnace Test，ImGui による露出とライトの調整                                                |
| **アーキテクチャ**   | ウィンドウの生成とメッセージループは App，描画は Engine，エンジンを使う側は Game とプロジェクトを分離．Builder パターンによる PSO とルートシグネチャの構築                              |

## レンダリングパイプライン

1フレームは以下の順で構成されます．

```
BeginFrame                 フレームレイテンシ待機 → フェンス同期 → コマンドリストのリセット
  │
  ├─ ShadowPass            directional light の視点から深度のみを描画する
  │                        影を落とすライトが無い場合は描画命令をスキップする
  │
  ├─ ScenePass             PBR + IBL + shadow で本描画する
  │                        露出とトーンマップを適用し，scRGB へ変換して出力する
  │
  ├─ SkyboxPass            深度テストを利用して背景部分にのみ環境キューブマップを描画する
  │                        こちらも同じトーンマップと scRGB 変換を通す
  │
  ├─ DebugUI               ImGui を UI 用レンダーターゲット（R8G8B8A8_UNORM）へ描画する
  │
  └─ CompositePass         UI をシーンへ合成する
                           ImGui の出力を sRGB として線形化し，同じ白レベルで scRGB へ揃える

EndFrame / Present
```

IBL に使うテクスチャ（equirectangular → キューブマップ → mip 生成 → irradiance map → prefiltered env map → BRDF LUT）は，起動時に CS で一度だけ計算します．

## 技術的な見どころ

### 1. 物理量で統一したライティングと露出

ライトの強度を無次元の明るさではなく，**光束[lm]・照度[lx]・光度[cd] という実世界の測光量**で扱っています．
たとえば point light は光束[lm]と影響範囲[m]で定義し，シェーダー側で光度[cd]・照度[lx]へ変換します．

これに合わせて，カメラ側も**絞り値・シャッタースピード・ISO 感度を持つ物理カメラ**として実装しました．
露出は EV100（ISO 100 における露出値．絞り値 N とシャッタースピード t[s] から `EV100 = log2(N² / t)` で求まる指標）で表現し，
そこから計算した露出倍率を線形色に掛けます．これによりライトの物理量とカメラ設定が同じスケールで結びつきます．

その結果，「屋外の直射日光 10万 lx」「屋内の作業場 500 lx」といった実測値をそのまま設定できます．
HDRI を差し替えた場合も，その HDRI が水平面に与える照度を実測値に合わせるだけで済み，露出設定を作り直す必要がありません．

この考え方の延長として，照明器具の配光を実測した **IES プロファイル** の読み込みにも対応しました．
光度[cd]の角度分布をファイルからそのまま光源に与えるため，内角・外角で円錐を切るだけのスポットライトでは作れない配光を再現できます．

![IES プロファイルによる配光](images/ies.webp)
_同じスポットライトに異なる IES プロファイルを適用した結果．上は中心が最も明るい配光，下は中心が暗くドーナツ状に広がる配光で，どちらもプロファイルの数値のみから得られている_

### 2. IBL と多重散乱エネルギー補償

split-sum 近似に基づく IBL を，起動時に CS で一度だけ計算しています．

- equirectangular から**キューブマップへの変換**と，ダウンサンプリングによる mip 生成
- **irradiance map**（拡散反射項）
- **prefiltered env map**（roughness ごとに mip へ格納した鏡面反射項）
- **BRDF LUT**（`(N・V, roughness)` に対する split-sum の第2項）

さらに，GGX の単一散乱モデルでは roughness が高いときにエネルギーが失われる問題に対して，
**多重散乱エネルギー補償**を，IBL と個々のライト（平行光源・点光源・スポットライト）の双方に実装しました．

### 3. HDR ディスプレイへの出力

内部を HDR リニア（`R16G16B16A16_FLOAT`）で処理するだけでなく，HDR ディスプレイへの出力にも対応しています．

- `IDXGIOutput6` からディスプレイの最大輝度・最小輝度・最大フルフレーム輝度と HDR 対応状況を取得する
- スワップチェインの色空間を scRGB（`RGB_FULL_G10_NONE_P709`）に設定する
- トーンマップに **GT トーンマップ**を使い，その最大輝度パラメータを `ディスプレイの最大輝度 / paper white 輝度` から決める
- 出力時に paper white 基準（HDR: 200 nits / SDR: 80 nits）で正規化した色を scRGB へ変換する
- ウィンドウが別のモニタへ移動したことを検出し，ディスプレイの情報を取得し直す

「1.0 が何 nits なのか」を最後まで明示的に扱うことで，SDR と HDR で同じシーンが同じ明るさに見えるようにしています．
色相のずれを防ぐため，トーンマップは max RGB を代表値として適用し，他のチャンネルはその比率で復元しています．

### 4. ハンドルによるオブジェクト管理と GPU リソースの寿命管理

D3D12 はリソースの寿命管理をアプリケーション側に委ねるため，GPU が使用中のリソースを破棄してしまう不具合が起こりやすい API です．
本プロジェクトでは CPU 側と GPU 側の2段構えで寿命を管理しています．

**CPU 側 — インデックスと世代番号を組にしたハンドル**

GameObject・Model・Light は生ポインタではなく，配列のインデックスと世代番号を組にしたハンドル `{index, generation}` で参照します（英語では generational index と呼ばれる手法です）．
削除されたスロットが再利用されても generation が一致しないため，解放済みオブジェクトへのアクセスを検出できます．
内部の `SlotMap` は実データを密な配列で保持しつつ，間接参照テーブルとフリーリストを持つことで，
O(1) の生成・削除とキャッシュ効率の良い一括走査を両立しています．

**GPU 側 — RAII と遅延解放**

| 仕組み                 | 役割                                                                            |
| ---------------------- | ------------------------------------------------------------------------------- |
| `DescriptorAllocation` | ディスクリプタヒープのスロットをスコープで確保・返却する                        |
| `AssetLoadScope`       | `ResourceUploadBatch` の Begin/End とアップロードヒープの破棄をまとめて管理する |
| `RetireQueue`          | GPU が実行中のリソースを即座に破棄せず，フレームを跨いで遅延解放する            |

### 5. Builder パターンによるパイプラインの構築

冗長になりがちな `D3D12_GRAPHICS_PIPELINE_STATE_DESC` やルートシグネチャの構築を，
`GraphicsPipelineBuilder` / `ComputePipelineBuilder` / `RootSignatureBuilder` のメソッドチェーンで記述できるようにしています．
描画パスを追加するたびに 100 行規模の記述を書く必要がなくなり，ShadowPass の追加時には深度クリップの無効化とカリングモードの指定だけで済みました．

## 品質確認の仕組み

実装したものが正しいかどうかを確認する手段を，機能と同時に用意しています．

### ImGui によるデバッグ UI

実行中の状態確認とパラメータ調整を，5つのパネルで行えます．F1 で表示 / 非表示を切り替えます．

| パネル       | 内容                                                                               |
| ------------ | ---------------------------------------------------------------------------------- |
| `Stats`      | FPS とフレーム時間                                                                 |
| `Camera`     | 露出（EV100 / 絞り値 / シャッタースピード）の調整と，カメラの位置・回転の表示      |
| `Light`      | 環境光の強度と，シーン内の各ライトの色・強度・向きの調整（ライトごとに折りたたみ） |
| `DebugView`  | 表示するデバッグビューの選択（次節）                                               |
| `Shadow Map` | シャドウマップの深度をそのまま表示                                                 |

`Camera` パネルは EV100 のスライダーに加えて「Sunny 16 / Indoor / Night」のプリセットを持ち，
**EV100 を動かしたときに絞り値とシャッタースピードのどちらを固定するか**を選べます．実際のカメラの絞り優先・シャッター優先と同じ操作です．
`Light` パネルの平行光源には「Daylight (5500K) / Blue Sky (10000K)」の色温度プリセットがあり，照度[lx]と方位・仰角を直接指定できます．

### White Furnace Test

輝度が一様に 1.0 の環境光の下で，albedo 1.0 の球を描画したときに，球が背景と同じ白さになるかを確認するテストです．
エネルギーが保存されていれば入射した光がすべて反射されるため，**球の輪郭が背景に溶けて見えなくなります**．

球は左から roughness 0 / 0.1 / 0.25 / 0.5 / 0.75 / 0.9 / 1.0 の7個を並べています．
roughness が低いほど失われるエネルギーが小さいため，補償がない場合も白くなり，見えなくなります．

|                                                          |                                                                      |
| -------------------------------------------------------- | -------------------------------------------------------------------- |
| ![](images/white_furnace_before.webp)                    | ![](images/white_furnace_after.webp)                                 |
| 多重散乱エネルギー補償なし．roughness が高いほど暗くなる | 補償あり．球の輪郭が消え，エネルギーが保存されていることが確認できる |

このテストによって，以下の不具合を発見して修正しました．

- 鏡面反射の計算で，フレネルの近似式を2回掛けてしまっていた
- GGX の重要度サンプリングで，本来使うべきサンプルを捨てていた

### PIX による GPU 時間の計測

各描画パスに [WinPixEventRuntime](https://github.com/microsoft/PixEvents) のマーカーを埋め込み，
[PIX for Windows](https://devblogs.microsoft.com/pix/) の GPU キャプチャでパスごとの GPU 時間を計測できるようにしています．
マーカーを有効にした `Profile` 構成を別に用意しているため，配布する Release ビルドには影響しません．

RTX 4070 / 1280×720 / デモシーンとデバッグ UI を表示した状態での実測値です．

| パス                     |     GPU 時間 |     割合 |
| ------------------------ | -----------: | -------: |
| Scene Pass               |     189.4 µs |      72% |
| Shadow Pass              |      25.6 µs |      10% |
| UI Pass（ImGui）         |      22.5 µs |       9% |
| Composite Pass           |       9.2 µs |       4% |
| Skybox Pass              |       8.2 µs |       3% |
| その他（リソースバリア） |       7.3 µs |       3% |
| **合計**                 | **262.3 µs** | **100%** |

144Hz の1フレーム 6.94 ms に対して，GPU の実作業は 0.26 ms でした．**フレーム時間の大半は VSync の待ちです．**

### 開発の進め方

- `.clang-format` によるフォーマットの統一．全体を再整形したコミットは `.git-blame-ignore-revs` に登録し，`git blame` の結果に影響しないようにしています
- 機能単位でブランチを切り，Pull Request 経由で main へマージしています
- シェーダーのコンパイルは FXC から DXC へ移行しました．FXC は Shader Model 5.1 までしか対応しておらず，SM 6.0 以降を使うには DXC が必要なためです

## ビルド方法

### 必要な環境

- Windows 11（Direct3D 12 に対応した GPU）
- Visual Studio 2022（v143 ツールセット．インストール時に「C++ によるデスクトップ開発」を選択）
- Windows 10 SDK 10.0 以降
- [vcpkg](https://github.com/microsoft/vcpkg)（`vcpkg integrate install` で Visual Studio と統合済みであること）

### 手順

```bash
git clone https://github.com/tsukikage22/d3d12-engine.git
cd d3d12-engine
```

HDRI・3D モデルはリポジトリに含めていません．
[Releases](https://github.com/tsukikage22/d3d12-engine/releases) の zip に含まれる `assets/` を，リポジトリの `assets/` に配置してください．
出典は [assets/CREDITS.md](assets/CREDITS.md) を参照してください．

`d3d12-engine.sln` を Visual Studio 2022 で開き，構成を `Release | x64` にしてビルドします．
依存ライブラリは `vcpkg.json` に記述してあり，ビルド時に自動で取得・ビルドされます（初回は時間がかかります）．

### ビルドせずに実行する

[Releases](https://github.com/tsukikage22/d3d12-engine/releases) に，実行ファイルとアセットをまとめた zip を置いています．
展開して `App.exe` を実行してください．

## 今後の予定

- アンチエイリアス（MSAA / SSAA）．フリップモデルのスワップチェインはバックバッファをマルチサンプル化できないため，どちらもシーンを一度オフスクリーンのレンダーターゲットへ描く構成への変更が前提になる
- point light / spot light のシャドウ
- カスケードシャドウマップによる広域シーンでの品質改善
- ポストプロセス（bloom，SSAO）
- 描画コマンドのバッチングとインスタンシングによる描画負荷の削減
- 本エンジンを静的ライブラリとして使うゲームを，別リポジトリで制作する
